**Byte-identical?** Yes — confirmed both by MD5 match and by independently comparing raw file byte-length for every member of each group (`size_bytes` matches within each group in all 9 cases).

**Source-data duplication vs. manifest/path-generation issue — what the evidence shows:**
- Each member of every pair has a **different `orig` value** (e.g., group 1: `20.jpg` vs `10260.jpg`), and `orig` is populated directly from the per-row image filename hint read out of the source parquet file (`tools/import_hf_parquet.py:140,156` — `b, hint = image_bytes(r[img])` then `"orig": hint or ""`), one hint per parquet row, with no merging or cross-row logic anywhere in the import path.
- Each member also belongs to a different official split's parquet shard set (train shards vs. val/test shards — confirmed by `split_of()` being keyed off shard filename, not content).
- `import_hf_parquet.py`'s loop (`do_import`, lines 136–161) writes exactly one output image per source parquet row it iterates, sequentially numbered per split; it does not deduplicate, compare, or reuse bytes across rows.
- Given that: two **distinct rows**, in **two distinct upstream shard groups** (i.e., distinct places in the source dataset), produced byte-identical image content under two different original filenames. Since this project's import step processes rows independently and never copies one row's bytes into another row's output, the only way both outputs end up byte-identical is if the source parquet data itself already contained the same image bytes twice, filed under two different `orig` ids, with the dataset's own official train/val or train/test split assignment placing the two copies in different splits.
- **Conclusion (no stronger claim made than the evidence supports):** the pattern is consistent with duplicate content pre-existing in the upstream IIIT-INDIC-HW-WORDS-Tamil dataset (i.e., the same handwriting sample scanned/stored twice under different ids and inconsistently split by the dataset's original authors), not with a bug in this project's manifest or path-generation code. This cannot be verified beyond what's observable from the two output artifacts (manifest + image bytes) without inspecting the original upstream parquet rows byte-for-byte a second, independent way — which was not done here, in keeping with "read-only, no further processing."

The manifest count (11,598) **matches the actual source parquet row count (11,598) exactly** — both independently recomputed in this investigation, not merely re-read from the earlier tool output. The `OFFICIAL` dictionary is a hardcoded literal in `check_split.py` (not derived from the parquet at runtime); its `val` entry is 1 lower than what the source data currently contains.

**Was the constant changed?** No — per your instructions, `tools/check_split.py` was not modified as part of this investigation (the earlier UTF-8 output fix touched only the stdout/stderr encoding lines, not the `OFFICIAL` dict).

**Does current evidence suggest the manifest should remain at 11,598?** Yes, on the evidence gathered: the manifest is a faithful, complete transcription of every row in the two validation parquet shards as they currently exist on disk (11,598 = 5,799 + 5,799, with 0 rows dropped for encodability — same as the train split's exact 75,736/75,736 match). There is no evidence in this investigation of any manifest-side row loss, duplication, or miscount for the val split. The 1-row gap is fully attributable to the hardcoded `OFFICIAL["val"]` reference value being stale or off by one relative to the currently-present source shards — not to a problem with the manifest. This investigation does not determine *why* the hardcoded constant says 11,597 (e.g., whether the original IIIT paper/release documented 11,597 and the shards were regenerated once more row was added upstream, or the constant was simply mistyped) — that would require information outside this repository.

## 3. Unusual-label rows containing Tamil numerals

`check_split.py` only prints the first 10 "unusual label" rows per split; the full, untruncated count is:

| Split | Unusual-label rows (full count) | Printed by check_split.py |
|---|---|---|
| train | **67** | 10 (of 67) |
| val | **2** | 2 (of 2) |
| test | **9** | 9 (of 9) |

The detection rule (`tools/check_split.py:53`) flags a label if it contains a space, a Latin letter, **or** is a full match of `[0-9௦-௯.,\-]+` (digits, Tamil digits U+0BE6–U+0BEF, periods, commas, hyphens). Every one of the 78 rows found across all three splits falls into this third case: the label is composed entirely of Tamil digit characters (U+0BE6 ௦ through U+0BEF ௯), representing two- or three-digit numbers written as digit sequences (e.g. `௭௮` = digits 7,8 → "78"; `௧௦௦` = digits 1,0,0 → "100"). No row in any split contains a space, a Latin letter, or a period/comma/hyphen variant — confirmed by re-running the identical regex condition against every manifest row and inspecting each match's Unicode codepoints individually.
